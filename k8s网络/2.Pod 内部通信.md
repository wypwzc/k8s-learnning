# 阶段二：Pod 内部通信（最微观）

经过第一阶段，你已经知道：

```
Pod ≈ Network Namespace
```

但 Kubernetes 有一个很奇怪的现象：

```
一个 Pod
↓
多个容器
↓
只有一个 IP
```

例如：

```
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
  - name: nginx
    image: nginx

  - name: busybox
    image: busybox
```

你会发现：

```
nginx容器
busybox容器

IP都是：
10.244.1.23
```

为什么？

因为：

```
Pod不是容器

Pod是共享资源容器组
```

而这个共享资源的拥有者：

```
Pause Container
```

------

# 一、Pause 容器（Infra Container）

## Pod 创建真实过程

很多人以为：

```
kubectl apply pod.yaml
↓
创建 nginx
↓
创建 busybox
```

实际上不是。

真实流程：

```
Kubelet
 ↓
CRI(containerd)
 ↓
创建 Pause Container
 ↓
创建 Network Namespace
 ↓
创建 veth
 ↓
配置 Pod IP
 ↓
启动 nginx
 ↓
启动 busybox
```

结构：

```
Pod
│
├── Pause
│     └── Network Namespace
│
├── nginx
│     └── 共享 Pause Namespace
│
└── busybox
      └── 共享 Pause Namespace
```

------

## 为什么必须有 Pause

思考：

如果没有 Pause

```
nginx退出
↓
namespace销毁

busybox怎么办？
```

无法共享。

因此 Kubernetes设计：

```
Pause 永远活着
```

负责：

```
保存 Pod Namespace
```

所以：

```
Pause ≈ Pod 的根
```

------

# 查看 Pause

查看 Pod：

```
kubectl get pod nginx -o wide
```

获取 Node。

进入 Node：

```
crictl ps
```

输出：

```
CONTAINER ID   IMAGE
abcd1234       pause:3.9
efgh5678       nginx
ijkl9012       busybox
```

你会发现：

```
每个 Pod 最先启动的是 pause
```

------

# 查看 Pause PID

```
crictl inspect <pause-id>
```

例如：

```
{
  "info": {
    "pid": 27831
  }
}
```

------

查看 Namespace：

```
ls -l /proc/27831/ns
```

输出：

```
net -> net:[4026532888]
ipc -> ipc:[4026532889]
uts -> uts:[4026532890]
```

说明：

```
Pause拥有：
Network Namespace
IPC Namespace
UTS Namespace
```

------

# 二、共享网络栈

------

## Network Namespace共享

nginx：

```
net:[4026532888]
```

busybox：

```
net:[4026532888]
```

Pause：

```
net:[4026532888]
```

完全一样。

------

验证：

进入 nginx

```
kubectl exec -it mypod -c nginx -- ip addr
```

看到：

```
eth0
10.244.1.23
```

进入 busybox

```
kubectl exec -it mypod -c busybox -- ip addr
```

也是：

```
10.244.1.23
```

------

这时候要改变认知：

不是：

```
容器有IP
```

而是：

```
Namespace有IP
```

------

# Pod IP 到底是谁的 IP

答案：

```
属于 Pause 的 Network Namespace
```

不是 nginx 的。

不是 busybox 的。

------

结构：

```
Pause Namespace
│
├── lo
│
└── eth0
     10.244.1.23
```

所有容器：

```
共享这个 Namespace
```

------

# 三、Loopback（127.0.0.1）

这是面试最爱问的。

------

## 普通容器

假设：

容器A

```
127.0.0.1
```

容器B

```
127.0.0.1
```

实际上：

```
两个不同 Namespace
```

所以：

```
A不能访问B的localhost
```

------

## Pod内部

情况不同：

```
nginx
busybox
```

共享同一个：

```
Network Namespace
```

因此：

```
127.0.0.1
```

也是共享的。

------

示例：

nginx：

```
python3 -m http.server 8080
```

busybox：

```
curl 127.0.0.1:8080
```

成功。

------

数据流：

```
busybox
   |
127.0.0.1
   |
lo
   |
nginx
```

甚至不会经过：

```
veth
bridge
iptables
```

完全在 Namespace 内部完成。

------

# Pod 内 localhost 通信路径

```
busybox
 ↓
socket()
 ↓
127.0.0.1
 ↓
lo
 ↓
Linux TCP/IP Stack
 ↓
nginx
```

------

# 验证

进入 Pod：

```
ip addr show lo
```

看到：

```
lo: UP
127.0.0.1/8
```

------

抓包：

```
tcpdump -i lo -nn
```

然后：

```
curl 127.0.0.1:8080
```

可以直接看到流量。

------

# 四、networkMode: container

Docker 早就支持这种模式。

例如：

```
docker run -d --name nginx nginx

docker run -it \
--network container:nginx \
busybox
```

------

结构：

```
nginx
   ↓
Network Namespace

busybox
   ↓
共享 nginx Namespace
```

------

这实际上就是：

```
Pod 的原型
```

Kubernetes 只是变成：

```
共享 Pause Namespace
```

------

# 五、IPC Namespace

------

查看：

```
ls -l /proc/<pid>/ns
```

你会看到：

```
ipc:[4026532889]
```

------

IPC包括：

```
共享内存
消息队列
信号量
```

------

例如：

容器A

```
创建共享内存
```

容器B

```
直接访问
```

------

网络共享：

```
共享IP
共享端口
```

IPC共享：

```
共享内存
共享消息队列
```

------

# 六、UTS Namespace

UTS控制：

```
hostname
domainname
```

------

Pod内部：

```
hostname
```

nginx：

```
mypod
```

busybox：

```
mypod
```

完全一样。

------

因为共享：

```
UTS Namespace
```

# 七、真实查看 Pod Namespace

## 方法1（Docker）

查看容器：

```
docker inspect <container-id>
```

关注：

```
{
  "HostConfig": {
    "NetworkMode": "container:pause"
  }
}
```

说明：

```
共享 Pause 网络栈
```

------

## 方法2（containerd）

获取 Pod：

```
crictl ps
```

查看：

```
crictl inspect <container-id>
```

找到：

```
{
  "info": {
    "pid": 27831
  }
}
```

------

进入宿主机：

```
lsns -t net
```

例如：

```
NS
4026532888
```

------

查看谁使用：

```
lsns -t net
```

输出：

```
NS           PID
4026532888   pause
4026532888   nginx
4026532888   busybox
```

说明：

```
三个容器共享同一个网络命名空间
```

```

```

数据包：

```

 ↓

```

不会经过：

```
eth0
veth
cni0
route
iptables
```

# 故障案例

## Sidecar 无法访问 localhost

例如：

```
App Container
127.0.0.1:8080

Sidecar
curl localhost:8080
失败
```

排查：

### 1 查看监听

```
ss -lntp
```

确认：

```
8080 LISTEN
```

------

### 2 查看绑定地址

错误：

```
127.0.0.1:8080
```

某些程序可能只监听 IPv6：

```
::1:8080
```

导致失败。

------

### 3 查看 Namespace

```
lsns -t net
```

确认：

```
同一个 net namespace
```

------

### 4 抓 loopback

```
tcpdump -i lo -nn
```

确认请求是否到达。

------

# 阶段二核心结论

牢记一句：

```
Pod ≠ Container

Pod = Network Namespace

Pause = Namespace 持有者

Pod IP = Namespace IP

localhost = Pod共享资源
```

所以：

```
一个 Pod
多个容器
一个 IP
一个 localhost
```

完全合理。

------

# 为阶段三铺垫

下一阶段开始进入 Kubernetes 网络最核心部分：

```
Pod A
   ↓
Pod B
```

即：

```
同节点 Pod 通信
跨节点 Pod 通信
```

你会看到：

```
PodA
 ↓
veth
 ↓
cni0
 ↓
veth
 ↓
PodB
```

以及：

```
PodA
 ↓
veth
 ↓
cni0
 ↓
Node1
 ↓
VXLAN/BGP
 ↓
Node2
 ↓
cni0
 ↓
PodB
```

这就是 CNI（Flannel/Calico/Cilium）真正工作的地方。

如果不理解本阶段，你会卡在：

```
为什么 Pod 只有一个 IP？
为什么 Pod 里的容器能共享 localhost？
为什么 Pause 容器必须存在？
```

而这些恰恰是理解 Pod→Pod 通信路径的前提。下一步就进入 Kubernetes 网络最核心的部分：**阶段三（同节点 Pod 通信 与 跨节点 Pod 通信）**。

# 阶段三：Pod 与 Pod 通信（同节点 & 跨节点）

终于进入 Kubernetes 网络的核心。

前两阶段解决了：

```
Pod = Network Namespace
Pod网卡 = veth
Node交换机 = cni0 bridge
```

现在开始回答 Kubernetes 网络最重要的问题：

> Pod A 的数据包是如何到达 Pod B 的？

------

# 先记住 Kubernetes 网络模型

Kubernetes 有一个非常重要的设计原则：

```
Every Pod can communicate with every other Pod
without NAT.
```

即：

```
任意 Pod
↓
任意 Pod
↓
直接通信
↓
不需要 NAT
```

例如：

```
PodA
10.244.1.2

PodB
10.244.1.3

PodC
10.244.2.5

PodD
10.244.3.8
```

都能直接访问：

```
ping PodIP
```

------

# 第一部分：同节点 Pod 通信

假设：

```
Node1
│
├── PodA 10.244.1.2
│
├── PodB 10.244.1.3
│
└── cni0
```

------

## 网络结构

```
                Node1

           +-----------+
           |   cni0    |
           +-----------+
             /      \
            /        \
      vethA          vethB
        |              |
     PodA           PodB
 10.244.1.2      10.244.1.3
```

------

# 通信过程

PodA：

```
ping 10.244.1.3
```

------

## 第一步

PodA 构造 ICMP 包

```
SRC IP:
10.244.1.2

DST IP:
10.244.1.3
```

------

同时封装二层头：

```
SRC MAC:
AA-AA-AA

DST MAC:
BB-BB-BB
```

------

问题：

PodA 怎么知道 PodB 的 MAC？

------

# ARP

PodA：

```
Who has 10.244.1.3 ?
Tell 10.244.1.2
```

广播到 bridge。

------

Bridge：

```
cni0
```

转发广播。

------

PodB 回复：

```
10.244.1.3 is BB-BB-BB
```

------

于是：

```
ARP Table
```

产生：

```
ip neigh
```

例如：

```
10.244.1.3 dev eth0 lladdr BB-BB-BB
```

------

# 第二步

数据进入 veth

```
PodA
 ↓
eth0
 ↓
vethA
```

------

# 第三步

进入 cni0

```
vethA
 ↓
cni0
```

------

Bridge 查询 FDB

```
bridge fdb show
```

例如：

```
BB-BB-BB -> vethB
```

------

于是：

```
直接转发
```

------

# 第四步

```
cni0
 ↓
vethB
 ↓
PodB
```

------

# 同节点通信完整路径图

```
PodA(10.244.1.2)
    eth0（网卡）
     ↓
vethA （网线）（宿主机端）
     ↓
   cni0 虚拟网桥（同节点交换机）
     ↓
vethB （宿主机端）
     ↓
    eth0
     ↓
PodB(10.244.1.3)
```

------

# 为什么不需要 NAT

因为：

```
源IP:
10.244.1.2

目标IP:
10.244.1.3
```

本来就可达。

所以：

```
IP 不变

MAC 变化
```

即可完成转发。

------

# 本质

同节点 Pod 通信：

```
Bridge 二层转发
```

不是：

```
路由
```

------

# 验证

Node 上：

```
bridge fdb show
```

查看：

```
MAC
↓
veth
```

映射关系。

------

# 抓包

Node：

```
tcpdump -i any -nn icmp
```

PodA：

```
ping 10.244.1.3
```

观察：

```
SRC=10.244.1.2
DST=10.244.1.3
```

始终不变。

------

------

# 第二部分：跨节点 Pod 通信

------

假设：

```
Node1
PodA
10.244.1.2

Node2
PodB
10.244.2.3
```

------

Node IP：

```
Node1
192.168.10.11

Node2
192.168.10.12
```

------

# 问题来了

PodA 发：

```
10.244.2.3
```

交换机认识吗？

不认识。

因为：

```
10.244.x.x
```

只是 Pod 网络。

物理网络只认识：

```
192.168.x.x
```

------

所以：

需要 CNI。

------

# Overlay 网络

代表：

```
Flannel VXLAN
```

------

# VXLAN 原理

原始包：

```
SRC:
10.244.1.2

DST:
10.244.2.3
```

------

外层再封装：

```
SRC:
192.168.10.11

DST:
192.168.10.12

UDP 4789
```

------

最终：

```
Outer Ethernet

Outer IP

UDP 4789

VXLAN Header

Inner Ethernet

Inner IP
```

------

# 封装过程

## PodA

发送：

```
10.244.1.2
 ↓
10.244.2.3
```

------

## Node1 Route Lookup

```
ip route
```

看到：

```
10.244.2.0/24
dev flannel.1
```

------

于是：

```
进入 flannel.1
```

------

## flannel.1

执行：

```
VXLAN Encapsulation
```

变成：

```
Outer IP

192.168.10.11
↓
192.168.10.12

UDP 4789
```

------

## 到 Node2

Node2：

```
收到 UDP 4789
```

------

VTEP：

```
flannel.1
```

解封装。

恢复：

```
10.244.1.2
↓
10.244.2.3
```

------

转发：

```
cni0
 ↓
PodB
```

------

# VXLAN 完整路径

```
PodA(10.244.1.2)
      ↓
    cni0网桥
      ↓
  flannel.1虚拟网卡 【封装入口】
      ↓
  VXLAN隧道封装（外层包填宿主机IP）
      ↓
宿主机物理网卡eth0(192.168.10.11)
      ↓
    物理局域网
      ↓
目标节点物理网卡eth0(192.168.10.12)
      ↓
  flannel.1 【内核解封装，拆掉外层IP头】
      ↓
    cni0网桥
      ↓
PodB(10.244.2.3)
```

------

# 抓包验证

Node1：

```
tcpdump -i eth0 -nn udp port 4789
```

会看到：

```
192.168.10.11
↓
192.168.10.12
UDP 4789
```

------

继续：

```
tcpdump -i flannel.1 -nn
```

看到：

```
10.244.1.2
↓
10.244.2.3
```

------

这就是：

```
封装前
封装后
```

的区别。

------

# Overlay 的代价

增加：

```
Outer Ethernet 14B

Outer IP 20B

UDP 8B

VXLAN 8B
```

约：

```
50 Bytes
```

------

所以：

```
MTU 1500
↓
1450
```

------

# 第三部分：Underlay 网络

代表：

```
Calico BGP
```

------

思想：

```
不封装
```

------

# Node 当路由器

Node1：

```
10.244.1.0/24
```

Node2：

```
10.244.2.0/24
```

------

BGP 宣告：

```
我负责：

10.244.1.0/24
```

------

Node2 宣告：

```
我负责：

10.244.2.0/24
```

------

于是：

Node1 路由表：

```
ip route
```

出现：

```
10.244.2.0/24 via 192.168.10.12
```

------

Node2：

```
10.244.1.0/24 via 192.168.10.11
```

------

# 数据包路径

```
PodA
10.244.1.2
   |
   |
Node1
   |
Route Lookup
   |
192.168.10.12
   |
Node2
   |
PodB
10.244.2.3
```

------

注意：

```
没有 VXLAN

没有 UDP4789

没有封装
```

------

# Overlay vs Underlay

| 项目   | Flannel VXLAN | Calico BGP |
| ------ | ------------- | ---------- |
| 封装   | 有            | 无         |
| 性能   | 较低          | 较高       |
| MTU    | 1450          | 1500       |
| 复杂度 | 低            | 高         |
| 跨公网 | 容易          | 困难       |
| 抓包   | UDP4789       | 原始IP     |

------

# 故障案例

## Pod 跨节点 Ping 不通

### 第一步

查看路由

```
ip route
```

确认：

```
10.244.2.0/24
```

存在。

------

### 第二步

查看 VXLAN

```
ip link show flannel.1
```

是否：

```
UP
```

------

### 第三步

抓 UDP4789

```
tcpdump -i eth0 udp port 4789
```

------

没有包：

```
路由问题
```

------

有包没回：

```
防火墙
```

------

### 第四步

查看防火墙

```
iptables -L -n

firewall-cmd --list-all
```

确保：

```
4789/udp
```

开放。

# 阶段三核心结论

Kubernetes Pod 通信本质只有两种：

## 同节点

```
Pod
 ↓
veth
 ↓
cni0
 ↓
veth
 ↓
Pod
```

核心：

```
Bridge 二层转发
```

------

## 跨节点

### Overlay

```
Pod
 ↓
cni0
 ↓
VXLAN
 ↓
Node Network
 ↓
VXLAN
 ↓
cni0
 ↓
Pod
```

核心：

```
封装
解封装
```

------

### Underlay

```
Pod
 ↓
Route
 ↓
Node Network
 ↓
Route
 ↓
Pod
```

核心：

```
BGP路由
```

# 为阶段四铺垫

到这里你已经解决：

```
Pod → Pod
```

通信。

但 Kubernetes 真正大量使用的是：

```
Pod → Service
```

例如：

```
curl 10.96.0.100
```

问题来了：

```
ClusterIP
根本不存在网卡

为什么能通信？
```

这就是下一阶段：

```
kube-proxy
iptables
IPVS
eBPF
Service
CoreDNS
Ingress
```

要解决的核心问题。这里会正式进入 Kubernetes 网络第二大核心：**Service 流量转发机制**。

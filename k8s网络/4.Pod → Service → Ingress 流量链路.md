# 阶段四：Pod → Service → Ingress 流量链路（Kubernetes 网络核心）

如果说阶段三解决的是：

```
Pod → Pod
```

那么阶段四解决的是 Kubernetes 使用频率最高的通信：

```
Pod → Service
```

例如：

```
curl http://nginx-service
```

或者：

```
curl 10.96.100.10
```

你每天都在用 Service。

但有个非常奇怪的问题：

```
ClusterIP 根本不存在
```

例如：

```
kubectl get svc

NAME           TYPE        CLUSTER-IP
nginx-service  ClusterIP   10.96.100.10
```

查看节点：

```
ip addr | grep 10.96.100.10
```

没有。

查看 Pod：

```
kubectl get pods -o wide
```

也没有。

那么：

```
10.96.100.10
```

到底是谁？

------

# 第一部分：Service 本质

很多人误以为：

```
Service = 一个代理
```

其实不是。

Service 本质：

```
Service
↓
一组 iptables/IPVS/eBPF 规则
↓
负载均衡到 Endpoint
```

------

例如：

```
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc

spec:
  selector:
    app: nginx

  ports:
  - port: 80
```

对应：

```
Service IP
10.96.100.10
```

后端：

```
PodA
10.244.1.2

PodB
10.244.2.3

PodC
10.244.3.4
```

------

# Endpoint

查看：

```
kubectl get endpoints nginx-svc
```

输出：

```
10.244.1.2:80
10.244.2.3:80
10.244.3.4:80
```

------

关系：

```
Service
    ↓
Endpoint
    ↓
Pod
```

因此：

```
Service 不保存流量

Endpoint 才是真实目标
```

------

# 第二部分：kube-proxy

------

每个 Node 都有：

```
kube-proxy
```

查看：

```
kubectl get pods -n kube-system
```

会看到：

```
kube-proxy-xxxxx
```

------

职责：

```
监听 Service
监听 Endpoint

生成转发规则
```

------

# kube-proxy 三种模式

------

## 模式1：iptables（最经典）

默认模式。

------

生成：

```
iptables -t nat -L
```

会出现：

```
KUBE-SERVICES

KUBE-SVC-XXXX

KUBE-SEP-XXXX
```

------

逻辑：

```
Service
↓
iptables DNAT
↓
Endpoint
```

------

## 模式2：IPVS

基于 Linux LVS。

查看：

```
ipvsadm -Ln
```

例如：

```
TCP 10.96.100.10:80

-> 10.244.1.2:80
-> 10.244.2.3:80
-> 10.244.3.4:80
```

------

特点：

```
哈希查找
```

而不是：

```
iptables 链式匹配
```

------

大规模集群：

```
1万个Service
```

IPVS 性能更好。

------

## 模式3：eBPF（Cilium）

最先进。

直接：

```
Socket
↓
eBPF
↓
Pod
```

绕过大量 iptables。

------

性能：

```
iptables < IPVS < eBPF
```

------

# 第三部分：Pod → Service 完整路径

假设：

```
PodA
10.244.1.2
```

访问：

```
Service
10.96.100.10
```

后端：

```
PodB
10.244.2.3
```

------

## 第一步

应用：

```
curl 10.96.100.10
```

------

产生：

```
SRC
10.244.1.2

DST
10.96.100.10
```

------

## 第二步

进入 Pod 网卡

```
PodA
 ↓
eth0
 ↓
veth
```

------

## 第三步

进入 Node

```
veth
 ↓
cni0
```

------

## 第四步

进入 NAT 表

```
PREROUTING
```

查看：

```
iptables -t nat -L PREROUTING -n
```

跳转：

```
KUBE-SERVICES
```

------

# Service DNAT

匹配：

```
DST=10.96.100.10
```

执行：

```
DNAT
```

改写：

```
10.96.100.10
↓
10.244.2.3
```

------

数据包变成：

```
SRC
10.244.1.2

DST
10.244.2.3
```

------

# 第五步

路由查找：

```
10.244.2.3
```

------

然后：

```
跨节点
或者
同节点
```

按照阶段三继续转发。

------

# 验证 DNAT

查看：

```
iptables -t nat -L KUBE-SERVICES -n --line-numbers
```

类似：

```
1 KUBE-SVC-ABCDE
tcp
10.96.100.10
tcp dpt:80
```

------

继续：

```
iptables -t nat -L KUBE-SVC-ABCDE -n
```

看到：

```
KUBE-SEP-1111
KUBE-SEP-2222
KUBE-SEP-3333
```

------

继续：

```
iptables -t nat -L KUBE-SEP-1111 -n
```

例如：

```
DNAT
10.244.1.2:80
```

------

# conntrack

很多人忽略它。

实际上：

```
iptables NAT
必须依赖 conntrack
```

------

查看：

```
conntrack -L
```

例如：

```
TCP
10.244.1.2:53211
↓

10.96.100.10:80

↓

10.244.2.3:80
```

------

作用：

记录：

```
原地址
转换后地址
```

------

返回流量：

```
PodB
↓
PodA
```

时：

```
自动反向 NAT
```

# 第四部分：DNS 解析链路

大部分场景：

```
curl nginx-svc
```

不是：

```
curl 10.96.100.10
```

------

# CoreDNS

查看：

```
kubectl get svc -n kube-system
```

例如：

```
kube-dns
10.96.0.10
```

------

流程：

```
Pod
 ↓
DNS Query

 ↓

CoreDNS

 ↓

10.96.100.10
```

------

然后：

```
ClusterIP
↓
DNAT
↓
Pod
```

------

```
Pod

 ↓

CoreDNS

 ↓

 ↓

Pod
```

# 为什么 ClusterIP 无法从集群外访问？

很多面试会问。

------

例如：

```
ClusterIP
10.96.100.10
```

你在笔记本：

```
curl 10.96.100.10
```

失败。

------

原因1：私有地址

```
10.96.0.0/12
```

只是：

```
集群内部网段
```

------

原因2：没有路由

你的电脑：

```
ip route
```

没有：

```
10.96.0.0/12
```

路由。

------

原因3：DNAT 规则不存在

Service 转发规则只存在：

```
Kubernetes Node
```

里面。

------

所以：

```
ClusterIP
不是真实IP

而是虚拟服务IP
```

------

# 第五部分：Pod → Node

------

假设：

```
curl 192.168.10.100:9100
```

访问 Node Exporter。

------

数据路径：

```
Pod
 ↓
veth
 ↓
cni0
 ↓
Route
 ↓
eth0
 ↓
Node Process
```

------

这里：

```
不经过 Service
```

直接路由。

------

# hostNetwork

例如：

```
spec:
  hostNetwork: true
```

------

这时：

```
Pod
=
Host Network Namespace
```

------

查看：

```
ip addr
```

直接看到：

```
eth0
192.168.10.100
```

而不是：

```
10.244.x.x
```

------

因此：

```
没有 veth
没有 cni0
没有 Pod IP
```

# 第六部分：Ingress

终于来到七层。

------

假设：

```
www.demo.com
```

对应：

```
ServiceA
```

------

```
api.demo.com
```

对应：

```
ServiceB
```

------

# 数据流

```
Browser
    |
    |
    v

Ingress Controller

    |
    |
    v

Service

    |
    |
    v

Pod
```

------

例如：

```
rules:
- host: api.demo.com
```

------

Ingress Controller（如 NGINX）：

收到：

```
Host: api.demo.com
```

匹配：

```
ServiceB
```

转发。

------

# TLS终止

浏览器：

```
https://api.demo.com
```

------

TLS 握手：

```
Browser
↓
Ingress Nginx
```

完成。

------

然后：

```
解密
↓
HTTP
↓
Service
↓
Pod
```

------

因此：

```
TLS Termination
```

发生在：

```
Ingress Controller
```

------

# L4 vs L7

------

## L4

依据：

```
IP
Port
```

转发。

例如：

```
NodePort
LoadBalancer
```

------

## L7

依据：

```
Host
Path
Header
Cookie
```

转发。

例如：

```
Ingress
Gateway API
```

# 故障案例

## Service 不通

检查：

------

### Endpoint

```
kubectl get endpoints
```

是否为空。

------

### Service

```
kubectl describe svc
```

------

### kube-proxy

```
kubectl logs kube-proxy
```

------

### iptables

```
iptables -t nat -L KUBE-SERVICES -n
```

------

### conntrack

```
conntrack -L
```

------

### 抓包

Node：

```
tcpdump -i any host 10.96.100.10
```

观察：

```
是否完成 DNAT
```

# 阶段四核心结论

牢记：

```
Service 不是进程
Service 不是网卡
Service 不是容器
```

而是：

```
Service
↓
Endpoint
↓
kube-proxy
↓
iptables/IPVS/eBPF
↓
DNAT
↓
Pod
```

------

# 为阶段五铺垫

到这里你已经理解：

```
Pod
Pod
Service
Ingress
```

如何通信。

下一阶段要切换视角：

从：

```
Pod视角
```

变成：

```
Node视角
```

你将看到：

```
Flannel
Calico
Cilium
```

到底在节点上干了什么：

```
谁创建路由？
谁创建 VXLAN？
谁维护 BGP？
谁写 iptables？
谁加载 eBPF？
```

这就是 Kubernetes 网络架构师必须掌握的 **阶段五：Node 与 Node 通信（宿主机层）**。

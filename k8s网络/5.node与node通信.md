# 阶段五：Node 与 Node 通信（宿主机层）

前面四个阶段，你一直站在 Pod 视角看网络：

```
Pod
 ↓
veth
 ↓
cni0
 ↓
Service
 ↓
Ingress
```

现在切换视角：

```
Node（宿主机）
```

因为 Kubernetes 网络真正的控制平面其实运行在 Node 上。

你会发现：

```
Pod不会自己创建网络
Pod不会自己写路由
Pod不会自己建VXLAN
Pod不会自己写iptables
```

真正干活的是：

```
Flannel
Calico
Cilium
kube-proxy
```

这些 Agent。

------

# 一、Node 到底管理什么？

假设集群：

```
Node1
192.168.1.10

Pod CIDR:
10.244.1.0/24
Node2
192.168.1.11

Pod CIDR:
10.244.2.0/24
Node3
192.168.1.12

Pod CIDR:
10.244.3.0/24
```

------

Kubernetes Controller Manager 分配：

```
Node1
负责：
10.244.1.0/24
Node2
负责：
10.244.2.0/24
Node3
负责：
10.244.3.0/24
```

------

问题来了：

Node1 怎么知道：

```
10.244.2.0/24
```

在 Node2？

------

答案：

```
CNI 插件
```

负责同步。

------

# 二、查看节点路由表

登录 Node：

```
ip route show
```

Flannel VXLAN 典型输出：

```
10.244.1.0/24 dev cni0

10.244.2.0/24 via 10.244.2.0 dev flannel.1

10.244.3.0/24 via 10.244.3.0 dev flannel.1

default via 192.168.1.1 dev eth0
```

------

含义：

```
本地 Pod
↓
cni0

远端 Pod
↓
flannel.1
```

------

所以：

PodA 发往：

```
10.244.2.5
```

时：

Linux 内核：

```
Route Lookup
```

匹配：

```
10.244.2.0/24
```

于是：

```
发给 flannel.1
```

进行 VXLAN 封装。

------

# 三、Flannel 到底干了什么？

很多人理解：

```
Flannel = VXLAN
```

其实不准确。

Flannel 是：

```
网络控制器
```

VXLAN 只是其中一种 Backend。

------

Node 上：

```
ps -ef | grep flanneld
```

看到：

```
flanneld
```

------

职责：

```
监听 Kubernetes API

获取所有 Node PodCIDR

维护 VXLAN VTEP

维护路由表
```

------

工作流程：

```
Node1上线

↓

获得 PodCIDR

10.244.1.0/24

↓

写入 etcd / API Server

↓

Node2同步

↓

生成 VXLAN 映射
```

------

# 查看 Flannel 接口

```
ip link show flannel.1
```

例如：

```
flannel.1
mtu 1450
vxlan id 1
```

------

查看 FDB：

```
bridge fdb show dev flannel.1
```

例如：

```
5e:29:0a:01:00:00 dst 192.168.1.11
```

------

表示：

```
Node2 VTEP
↓
192.168.1.11
```

# 四、Flannel VXLAN 通信全过程

假设：

```
PodA
10.244.1.2
```

访问：

```
PodB
10.244.2.3
```

------

Node1：

路由：

```
10.244.2.0/24
↓
flannel.1
```

------

封装：

```
Outer IP

SRC:
192.168.1.10

DST:
192.168.1.11

UDP 4789
```

------

物理网络：

```
交换机
路由器
```

只看到：

```
192.168.1.10
↓
192.168.1.11
```

------

Node2：

```
flannel.1
```

解封装。

恢复：

```
10.244.1.2
↓
10.244.2.3
```

------

送入：

```
cni0
```

最终：

```
PodB
```

# 五、Flannel Host-GW 模式

很多人忽略这个模式。

------

VXLAN：

```
封装
```

Host-GW：

```
不封装
```

------

路由表：

```
ip route
```

输出：

```
10.244.2.0/24 via 192.168.1.11

10.244.3.0/24 via 192.168.1.12
```

------

意思：

```
Node1知道：

10.244.2.0/24
在Node2
```

直接转发。

------

路径：

```
PodA

↓

Node1

↓

Node2

↓

PodB
```

------

没有：

```
UDP4789
VXLAN Header
```

------

优点：

```
性能高
```

------

缺点：

```
要求二层网络互通
```

------

# Flannel Host-GW vs VXLAN

| 项目       | Host-GW | VXLAN |
| ---------- | ------- | ----- |
| 封装       | 无      | 有    |
| 性能       | 高      | 中    |
| MTU        | 1500    | 1450  |
| 跨三层网络 | 差      | 好    |
| 配置难度   | 高      | 低    |

# 八、MTU 问题

这是线上高频故障。

------

普通网络：

```
MTU=1500
```

------

VXLAN：

增加：

```
Outer Ethernet

Outer IP

UDP

VXLAN
```

约：

```
50 Bytes
```

------

因此：

```
1500
↓
1450
```

------

查看：

```
ip link
```

例如：

```
flannel.1 mtu 1450
```

------

故障现象：

```
ping 通

curl 卡住

大文件失败
```

------

检查：

```
ping -M do -s 1472 <IP>
```

------

如果失败：

```
MTU 不匹配
```

------

# 阶段五核心结论

站在 Node 视角看：

```
Pod 网络
=
Node 网络 + CNI 控制
```

真正负责网络的是：

| 插件    | 核心组件     | 作用          |
| ------- | ------------ | ------------- |
| Flannel | flanneld     | VXLAN/Host-GW |
| Calico  | felix + bird | Route + BGP   |
| Cilium  | cilium-agent | eBPF          |

------

Node 的核心任务：

```
维护 PodCIDR

维护路由表

维护隧道

维护iptables/eBPF

转发 Pod 流量
```

------

# 为阶段六铺垫

到这里你已经理解：

```
Pod ↔ Pod

Pod ↔ Service

Node ↔ Node
```

下一阶段解决最后一个问题：

```
Pod ↔ Internet
Internet ↔ Pod
```

即：

```
SNAT
MASQUERADE

NodePort

LoadBalancer

Ingress

externalTrafficPolicy
```

以及面试最爱问的：

```
为什么 Pod 能访问公网？

为什么公网不能直接访问 Pod？

NodePort 到底转发了几次？

LoadBalancer 和 Ingress 的区别是什么？
```

这就是 Kubernetes 网络体系的最后一块拼图：**阶段六（Node 与外网通信）**。

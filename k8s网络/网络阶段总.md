你好。Kubernetes 的网络栈因其涉及从内核级到应用层的大量抽象，通常被认为是整个云原生领域最难啃的骨头。作为一名在内核与容器网络摸爬滚打多年的从业者，我很理解这种痛点：很多时候我们不是不懂 K8s，而是缺乏对底层 Linux 网络原语的掌握，导致排查问题时如同盲人摸象。

今天，我们将严格遵循“微观到宏观、由内到外”的逻辑，扒开这层复杂的皮，直击 K8s 网络通信的本质。准备好终端，我们开始。

### 阶段一：网络基础概念与核心组件（地基层）

在 K8s 诞生之前，Linux 就已经具备了构建隔离网络的所有积木。K8s 的网络插件（CNI）本质上只是这些积木的自动化组装工。

- **Linux 网络命名空间 (netns)**：它是网络栈的克隆。每个 netns 有独立的路由表、iptables 规则、网卡。这是 Pod 网络隔离的物理基础。
- **veth pair**：虚拟以太网线，永远成对出现。它就像一根网线的两端，一头插在主机的命名空间，另一头插在 Pod 的命名空间，实现跨命名空间的数据“穿透”。
- **Linux Bridge**：虚拟交换机。基于 MAC 地址表进行二层转发（`brctl show` 可看挂载的设备）。当有多个 veth pair 存在时，Bridge 将它们连接在同一个局域网内。
- **路由表 (Route Table)**：三层转发地图。`ip route` 决定了数据包的下一跳（Next Hop）。K8s 节点之间的通信高度依赖路由表对 Pod 网段（CIDR）的精确指向。
- **iptables/netfilter**：内核包过滤与修改框架。四表五链是 Service 负载均衡（DNAT）和外网访问（SNAT）的核心引擎。
- **VXLAN**：K8s 最常用的 Overlay 隧道技术。通过 VTEP 设备，将原始以太网帧封装进 UDP（默认端口 4789）报文中，实现在跨节点的三层网络上构建大二层网络。

**动手实验：手工模拟单节点 Pod 网络**

请在任意一台 Linux 机器上依次执行以下命令，这就是 Docker/K8s 创建网络底层所做的事情：

Bash

```
# 1. 创建两个独立的网络命名空间（模拟两个 Pod）
ip netns add pod1
ip netns add pod2

# 2. 创建一个网桥（模拟 cni0 或 docker0）并启动
ip link add name br0 type bridge
ip link set br0 up

# 3. 创建两对 veth pair（网线）
ip link add veth1 type veth peer name veth1-pod
ip link add veth2 type veth peer name veth2-pod

# 4. 把一端插到 Pod 中，并分配 IP（模拟 CNI 分配 IP）
ip link set veth1-pod netns pod1
ip netns exec pod1 ip addr add 10.0.0.1/24 dev veth1-pod
ip netns exec pod1 ip link set veth1-pod up
ip netns exec pod1 ip link set lo up

ip link set veth2-pod netns pod2
ip netns exec pod2 ip addr add 10.0.0.2/24 dev veth2-pod
ip netns exec pod2 ip link set veth2-pod up
ip netns exec pod2 ip link set lo up

# 5. 把另一端插到网桥上，并启动
ip link set veth1 master br0
ip link set veth1 up
ip link set veth2 master br0
ip link set veth2 up

# 6. 测试连通性（Pod1 呼叫 Pod2）
ip netns exec pod1 ping 10.0.0.2
```

**故障排查案例**：如果上述实验 ping 不通，多半是因为 Linux 内核的安全机制拦截了网桥转发。排查思路：执行 `iptables -P FORWARD ACCEPT` 放行转发规则，或检查内核参数 `sysctl net.ipv4.ip_forward` 是否为 1。

> **阶段一总结与串联**
>
> **核心结论**：容器网络本质上是 netns 隔离的，通过 veth 接入网桥实现同节点互通。
>
> **下一阶段铺垫**：我们已经手动给一个 netns 分配了 IP，但在 K8s 中，一个 Pod 里面可能有多个容器，它们是如何共享这一个 10.0.0.1 的？
>
> **跳过风险**：如果不理解 veth pair 和网桥，在排查同节点 Pod 网络不同时，将无法定位是 CNI 插件挂载失败还是网桥路由异常。

### 阶段二：Pod 内部通信（最微观）

在 K8s 中，网络资源的最小分配单位是 Pod，而不是单一容器。

- **Pause 容器（Infra 容器）**：每当 K8s 启动一个 Pod，它会第一个拉起一个非常小的镜像（通常叫 `k8s.gcr.io/pause`）。这个容器什么都不干，只负责“占住”一个 Linux Network Namespace。
- **共享网络栈**：Pod 内后续启动的所有业务容器，在启动时都会加上类似 `docker run --net=container:<pause-container-id>` 的参数。这意味着所有业务容器直接使用 Pause 容器的网卡、IP 地址、路由表和 iptables。Pod IP 就是 Pause 容器的 IP。
- **Loopback 接口**：因为共享了同一个 netns，容器 A 监听了 `127.0.0.1:8080`，容器 B 就可以直接通过 `curl 127.0.0.1:8080` 访问。
- **IPC/UTS 命名空间**：除了网络，K8s 还会让 Pod 里的容器共享 IPC（进程间通信，可通过共享内存通信）和 UTS（主机名，Pod 内的主机名统一为 Pod 名称）。但 PID 和 Mount 命名空间默认依然是隔离的。

**动手实验：透视 Pod 的共享网络栈**

找到你的 Node 节点，通过 `crictl` 检查底层容器配置：

JSON

```
# 获取一个 Pod 的具体容器 ID
# crictl inspect <container-id> | grep -A 5 "namespaces"
"namespaces": {
  "network": {
    "mode": "CONTAINER",
    "container_id": "a1b2c3d4e5f6..." // 这里指向的就是 pause 容器的 ID
  },
  "pid": {
    "mode": "POD" // 根据 k8s 配置可能共享也可能隔离
  }
}
```

**故障排查案例**：一个 Pod 内包含 Nginx 和 Tomcat，启动报错 `Address already in use`。解决思路：这正是因为共享网络栈，两个容器都尝试绑定同一个端口（如 80）。必须修改其中一个的配置，Pod 内部端口不能冲突。

> **阶段二总结与串联**
>
> **核心结论**：Pod 内的容器网络是一体的，Pause 容器是基石。
>
> **下一阶段铺垫**：当 Pod 的数据包要离开 Pause 容器的 netns，前往另一个机器上的 Pod 时，该如何穿越宿主机？
>
> **跳过风险**：如果不理解共享机制，排查 Istio/Envoy Sidecar 流量劫持原理时会完全一头雾水。

### 阶段三：Pod 与 Pod 通信（同节点 & 跨节点）

这是 CNI（Container Network Interface）插件大显身手的地方。

**1. 同节点 Pod-Pod 通信**

- **数据包路径**：Pod A (10.244.0.2) -> vethA -> cni0 (Bridge) -> vethB -> Pod B (10.244.0.3)。
- **转发机制**：纯纯的二层转发。由于目标 IP 属于同一个子网（比如 10.244.0.0/24），数据包在发出前通过 ARP 请求获取目标 MAC，然后网桥 `cni0` 直接根据 MAC 地址表（`bridge fdb` 可看）将包送到目标 veth，**无需 NAT**。

**2. 跨节点 Pod-Pod 通信 (以 Flannel VXLAN 为例)**

- **数据包路径**：Pod A (Node 1) -> vethA -> cni0 -> Node 1 路由表 -> flannel.1 (VTEP 设备) -> UDP 封装 -> Node 1 物理网卡 eth0 -> Node 2 物理网卡 eth0 -> 解封装 -> flannel.1 -> Node 2 路由表 -> cni0 -> vethB -> Pod B。
- **Overlay (覆盖网络) 特征**：数据包的原始以太网帧（源 MAC、源 Pod IP）被打包在一个 UDP 报文中。外部网络只能看到 Node 1 的 IP 发送 UDP 4789 给 Node 2 的 IP。
- **Underlay (底层网络) 特征 (如 Calico BGP)**：不进行封装。Node 被当成真实的路由器，利用 BGP 协议在机房网络中宣告："要去 10.244.1.0/24（Pod B 网段），请把包发给我"。

**动手实验：抓包对比**

分别在同节点和跨节点的情况下，在目标 Node 的物理网卡上抓包：

Bash

```
# 同节点测试：在 Node1 抓包（仅抓到原始 ICMP，二层直通）
tcpdump -i any icmp -n

# 跨节点测试：在 Node2 物理网卡 eth0 抓包（抓不到 ICMP，只能抓到 UDP 隧道报文）
# 可以看到外层是 Node IP，目标端口 4789
tcpdump -i eth0 udp port 4789 -n
```

**故障排查案例**：Pod Ping 同节点 Pod 正常，Ping 跨节点 Pod 丢包。解决思路：绝大多数情况是因为跨节点的物理网络中途的防火墙/安全组阻断了 UDP 4789 端口（VXLAN）或 IP-in-IP（协议号 4）报文。

> **阶段三总结与串联**
>
> **核心结论**：跨节点通信要么通过隧道封装骗过底层网络（Overlay），要么通过 BGP 宣告让底层网络认识 Pod IP（Underlay）。
>
> **下一阶段铺垫**：Pod-Pod 通信是 IP 直连，但在 K8s 中 Pod IP 是动态变化的，业务只能访问不变的 Service IP，这就引入了下一层的抽象。
>
> **跳过风险**：如果不清楚 CNI 做了什么，排查跨可用区/跨网段丢包时将无从下手。

### 阶段四：Pod 到 Node / Service / Ingress 的流量链路

这里涉及 K8s 网络最核心的服务发现与 L4/L7 负载均衡机制。

- **ClusterIP 的本质**：Service 的 ClusterIP 是一个完全虚拟的 IP，即**VIP**。它不绑定在任何真实的物理网卡或虚拟网卡上。这也是为什么在集群外部即使配置了路由也 ping 不通它的原因——没有网卡会响应对这个 IP 的 ARP 请求。
- **kube-proxy 工作模式**：它在每个节点上监控 Service 变化，并生成转发规则。
  - **iptables**：基于长链条的包过滤规则，按顺序线性匹配，Service 过多时性能衰减严重。
  - **IPVS**：基于 Linux 内核的 L4 负载均衡模块，采用哈希表存储，复杂度为 O(1)，性能极佳。
  - **eBPF (如 Cilium)**：直接在网卡 XDP/TC 层拦截数据包进行转发，完全绕过 netfilter 栈，目前性能天花板。
- **DNS 解析**：Pod 访问 `svc-name` -> CoreDNS 返回 VIP -> 命中节点 iptables DNAT。
- **Ingress 控制器**：这是 L7 层。外部请求先达到 Ingress Pod，Nginx/Traefik 根据 HTTP Header 中的 `Host` 字段判断转发到哪个后端的 Service。TLS 终止（解密）发生在这里。

**动手追踪：一次 `curl <service-ip>` 的完整旅程**

路径：Pod -> veth -> cni0 -> 宿主机 PREROUTING 链 -> KUBE-SERVICES 链 -> KUBE-SVC-XXX 链 (按权重选中一个 Pod) -> KUBE-SEP-XXX 链 (执行 DNAT 改写目标 IP 为实际 Pod IP) -> 宿主机路由表 -> 目标节点。

Bash

```
# 查看某个 Service 的具体 iptables 规则链转换
# 这里能清晰看到目标从 ClusterIP 被改写为具体的后端 Endpoint IP
iptables -t nat -L KUBE-SERVICES -n --line-numbers
```

**故障排查案例**：`curl <cluster-ip>` 报错超时，但直接访问背后的 Pod IP 却通。解决思路：检查本节点的 `kube-proxy` 进程是否存活。或者用 `conntrack -L` 查看系统的连接追踪表是否满了（`nf_conntrack: table full, dropping packet`），导致新连接无法建立 NAT。

> **阶段四总结与串联**
>
> **核心结论**：Service 是宿主机级别的 DNAT 规则拦截，ClusterIP 只是触发这条规则的诱饵。
>
> **下一阶段铺垫**：我们知道了宿主机会转发这些包，但宿主机如何知道目标 Pod IP 在集群里的哪一台服务器上？
>
> **跳过风险**：不懂 Service 原理，就会试图去给 ClusterIP 配置静态路由，犯下南辕北辙的错误。

### 阶段五：Node 与 Node 通信（宿主机层）

这部分是集群网络的大脑中枢，决定了节点之间如何“认路”。

- **Node 网卡与 Pod CIDR**：K8s 的 Controller Manager 会为每个 Node 分配一个独立的 Pod CIDR（如 Node1: 10.244.1.0/24，Node2: 10.244.2.0/24）。节点之间通信必须知晓这个对应关系。
- **CNI 在节点的角色差异**：
  - **Flannel (VXLAN)**：`flanneld` 监听 K8s API，当发现新节点加入，它会在当前节点添加一条路由（目标是新 Pod CIDR，设备是 flannel.1），并在内核 FDB（转发数据库）中注入 VTEP 的 MAC 与宿主机真实 IP 的映射。
  - **Flannel (host-gw)**：不创建隧道设备。直接在宿主机写入静态路由：`去往 10.244.2.0/24 的包，下一跳直接发给 Node 2 的 eth0 IP`。这要求 Node1 和 Node2 必须在同一个物理二层网络。
- **MTU 问题**：标准以太网 MTU 是 1500。VXLAN 封装需要增加外层 IP 头(20) + UDP 头(8) + VXLAN 头(8) + 内层 MAC 头(14) = 50 字节。因此隧道设备 `flannel.1` 和 Pod 内的 `eth0` MTU 通常被设为 1450。如果配置不一致，大包会被无情丢弃且没有明显报错。

**动手实验：阅读宿主机路由表**

登录任意 K8s Node 执行：

Bash

```
# 解读：去往 10.244.1.0/24 (Node2 的 Pod 们) 的流量，
# 通过 flannel.1 发送，下一跳是 10.244.1.0 (对端 VTEP IP)
ip route show
# 输出示例: 10.244.1.0/24 via 10.244.1.0 dev flannel.1 onlink
```

**故障排查案例**：跨节点大文件传输（如 Java 上传日志或大文件）频繁断开，小包测试却正常。排查思路：高度怀疑 MTU 不一致引发的分片问题。用 `ping -s 1472 <pod-ip>` 发送不分片大包验证。解决方法：统一修改 CNI 的 MTU 配置。

> **阶段五总结与串联**
>
> **核心结论**：节点的路由表是整个 K8s 网络的心智地图，CNI 的核心工作就是维护这张地图。
>
> **下一阶段铺垫**：目前所有的流量都在集群内部打转（内网）。如果 Pod 需要去拉取 Docker Hub 的公网镜像，或者用户的公网请求要进来，边界流量怎么处理？
>
> **跳过风险**：不理解节点路由，集群节点一多、网络稍微复杂就会面临“不知包往哪飞”的黑盒状态。

### 阶段六：Node 与外网通信（外部访问入口 & 出口）

打通 K8s 孤岛与现实物理世界。

**1. 出方向（Pod -> Internet）**

- **SNAT / MASQUERADE**：公网路由器不认识 Pod 的私有网段（如 10.244.x.x），如果直接发出去，回程包根本找不到路。
- **机制**：当 Pod 的包离开 Node 物理网卡前，`iptables POSTROUTING` 链会将其源 IP 伪装（MASQUERADE）为宿主机的公网/物理网卡 IP。外网看来，就是这个 Node 在上网。

**2. 入方向（Internet -> Pod）**

- **NodePort 路径**：外网 -> 访问任意 `<NodeIP>:30080` -> 命中 `KUBE-NODEPORTS` iptables 链 -> DNAT 改目标为具体的后端 Pod IP -> 转发到对应 Node -> 抵达 Pod。
- **LoadBalancer**：云厂商监听 Service 创建事件，自动在云端创建一个 L4 负载均衡器（如 AWS ELB / 阿里云 SLB），将流量代理到集群各节点的 NodePort 上。
- **外部流量策略 (externalTrafficPolicy)**：
  - **Cluster (默认)**：包到达节点后，可能被 NAT 到其他节点上的 Pod。有额外一跳网络开销，且丢失客户端源 IP。
  - **Local**：包到达节点后，只转给本节点的 Pod。保留源 IP，无额外跳转。但如果本节点没有该 Pod，包直接丢弃（云 LB 会通过健康检查将其踢除出后端池）。

**动手实验：验证 `externalTrafficPolicy` 行为**

Bash

```
# 开启服务 NodePort 后，在另一台机器发起请求
curl http://<Node-IP>:<NodePort>

# 同时在 Node 上抓包，观察客户端 IP 到底是谁
# 若为 Cluster 模式，抓到的包源 IP 通常变成了另一台 K8s Node 的 IP (SNAT 效应)
tcpdump -i any port <NodePort> -n
```

**故障排查案例**：Service 改为 `externalTrafficPolicy: Local` 后，外部访问突然超时。排查思路：检查你访问的那个 Node 上到底有没有该 Service 的后端 Pod（`kubectl get pods -o wide`）。没有的话，请求到了该 Node 就会被直接丢弃。

### 核心汇总：K8s 网络全景对比表

**表 1：K8s 流量链路本质差异**

| **通信场景**       | **关键机制**          | **是否需要 NAT (地址转换)** | **经过宿主机路由表？** |
| ------------------ | --------------------- | --------------------------- | ---------------------- |
| 同节点 Pod 互访    | cni0 网桥 MAC 寻址    | **否** (直连)               | 否                     |
| 跨节点 Pod 互访    | 隧道封装 / BGP 路由表 | **否** (直连)               | 是                     |
| Pod 访问 Service   | kube-proxy 规则拦截   | **是** (DNAT 改目标)        | 是                     |
| Pod 访问 外网      | iptables 伪装策略     | **是** (SNAT 改源)          | 是                     |
| 外网 访问 NodePort | iptables 转发策略     | **是** (DNAT 改目标)        | 是                     |

**表 2：Service 转发引擎对比**

| **引擎**     | **底层技术**           | **复杂度 / 性能**       | **适用场景**           | **局限性**                                  |
| ------------ | ---------------------- | ----------------------- | ---------------------- | ------------------------------------------- |
| **iptables** | netfilter 线性链表过滤 | O(n) / 规则 > 5000 变慢 | 默认模式，兼容性极好   | 规则过多时，节点 CPU 飙高，更新规则极慢     |
| **IPVS**     | LVS 哈希表负载均衡     | O(1) / 极高             | 大规模集群首选         | 需要内核加载特定模块，排查难度略升          |
| **eBPF**     | 内核沙盒字节码挂载     | O(1) / 极致原生性能     | 追求极致性能与可观测性 | 要求内核版本高 (>=4.19)，脱离 iptables 体系 |

K8s 的网络栈看起来眼花缭乱，但万变不离其宗。只要在脑海里建立起“数据包从哪来、经过哪个接口、被哪条规则改写、下一跳去哪”的立体地图，任何诡异的网络延迟、丢包或不通现象，最终都会成为 `tcpdump`、`ip route` 和 `iptables` 输出中的清晰结论。希望这条自下而上的演进之路，能帮你彻底打通 K8s 网络任督二脉。
